the problem

Most of what happens after a meeting, doesn't.

The call goes fine. It's everything downstream of it — the notes, the tasks, the "I'll follow up" — that quietly falls apart.

Too many meetings

Back-to-back calls leave no room to write anything down properly, let alone act on it.

Manual note-taking

Typing while listening means doing both badly — or picking one and losing the other.

Missed action items

"Someone" was going to own that task. It never made it into anyone's tracker.

Scattered information

The decision lives in a call recording, the task lives in someone's head, the recap lives nowhere.

Forgotten follow-ups

By the time you're free to write the recap, the moment — and half the detail — is gone.

how it works

One folder in. A finished trail of work out.

Six stages, running in a fixed sequence for every transcript that lands in the watch folder. Nothing here waits on you until the very last one.

  1. 01

    Meeting

    Your call tool records it — Zoom, Teams, Meet, or a transcription bot like Otter, Fireflies, or Fathom.

  2. 02

    Transcript

    Exported as .txt and dropped into WATCH_FOLDER. The one deliberately manual step.

  3. 03

    AI processing

    watcher.py confirms the file's done writing, then sends it to Claude (or a local Ollama model) for structured extraction.

  4. 04

    Summary

    A 2–4 sentence summary and a list of key decisions come back as one strict JSON object — no free text to re-parse.

  5. 05

    Action items

    Each item becomes a real task in Asana or Notion, with an owner and due date where the transcript gave one. One item failing doesn't block the rest.

  6. 06

    Follow-up

    Claude drafts a recap and posts it — with task links — to a private Slack channel. You read it before anyone else does.

a day with the assistant

What automatic actually looks like

The human parts of this take minutes. The automated parts take seconds. That gap is the entire point.

  1. 9:00 AM
    you

    Discovery call with a prospective client, transcription running in the background.

  2. 9:47 AM
    you

    Call ends. You export the transcript and drop acme-discovery-call.txt into WATCH_FOLDER. That's your last manual step.

  3. 9:47:12 AM
    automatic

    watcher.py notices the new file and waits for its size to stop changing before touching it.

  4. 9:47:14 AM
    automatic

    Claude reads the transcript: a summary, 3 key decisions, and 4 action items come back as structured JSON.

  5. 9:47:19 AM
    automatic

    4 tasks are created in Asana, each with an owner and due date. One extra task with no clear owner is skipped and flagged, not guessed at.

  6. 9:47:24 AM
    automatic

    A follow-up recap is drafted and posted to #meeting-review on Slack, with links to every task that was created.

  7. 9:52 AM
    you

    You skim the Slack draft, tighten one sentence, and send it to the client yourself. Nothing reaches them without you reading it first.

  8. 5:30 PM
    manager

    End of day: the dashboard shows 6 meetings processed, 0 sitting in failed/, and every follow-up sent — without anyone chasing it down.

business impact

What it actually buys you

Time back

No transcribing, no formatting a recap, no re-typing action items into a tracker by hand.

Less admin overhead

Task creation and follow-up drafting stop being someone's Tuesday-afternoon chore.

Real accountability

Every action item gets an owner and a due date in the system your team already tracks work in.

Consistent follow-ups

Every meeting gets a recap drafted the same way, whether it's your first call that day or your sixth.

automation architecture

What's actually running underneath

No workflow-builder in the middle — a single Python process watches the folder and drives a fixed pipeline. This is the real shape of it, not a simplified diagram.

input .txt transcript dropped in WATCH_FOLDER
automation layer watcher.py watchdog · stability check
ai processing Claude / Ollama structured JSON extraction
output Dashboard + Slack FastAPI/Jinja2 · review message
business tools Asana / Notion + Slack Incoming Webhook
storage SQLite storage.py · WAL mode

Two long-running processes share the database: watcher.py writes a run row and a heartbeat, run_dashboard.py only ever reads. The dashboard can't affect the pipeline — it's a spectator, on purpose.

why businesses need it

It's an automation system, not a chatbot

Nobody has to remember to open it, prompt it, or ask it anything. It runs on a trigger you already produce — a finished transcript — and stops at the one point that needs a human.

A chatbot

  • Only does something if someone remembers to ask it
  • Lives in a chat window, disconnected from your tools
  • Answers questions; doesn't file anything anywhere

This system

  • Triggers itself the moment a transcript exists
  • Writes directly into Asana/Notion and Slack — real systems of record
  • Still stops for a human review before anything reaches a client

technical implementation

How it's actually built

runtime

Python 3, single long-running process (watcher.py)

file watching

watchdog, with a write-stability check so partial uploads aren't processed mid-copy

ai processing

Claude (claude-sonnet-5), structured JSON extraction, extended thinking explicitly disabled so it can't silently eat the output token budget

local ai option

Ollama (llama3.1) as a config swap — runs fully offline, no API key required

task backends

Asana or Notion, chosen by one config value; task creation is per-item fault-tolerant

follow-up delivery

Slack Incoming Webhook, posted only to a private review channel — never direct to attendees

persistence

SQLite via stdlib sqlite3, WAL mode so the watcher and dashboard don't lock each other out

dashboard

FastAPI + Jinja2, read-only: run history, per-run detail, live watcher status

testing

91 automated tests (pytest), all against mocked API clients — zero live network calls

Fault isolation, deliberately: every pipeline stage is wrapped so one bad transcript can't take down the watcher, one failed task creation can't block the others, and a database write failure can never block the pipeline itself — it only costs dashboard visibility for that run. Files that fail move to failed/ with the error logged; nothing disappears silently.
